## 0. 왜 하나

**한 줄:** 칩을 설계할 때 열 검사가 너무 느려서 제대로 못 하고 있는데, AI가 그걸 순식간에 해 주면 설계하는 내내 열을 볼 수 있다.

1. **지금의 문제**
   칩 위에 블록(코어, 캐시 등)을 놓는 배치 작업은 컴퓨터가 위치를 수만 번 바꿔 보며 좋은 배치를 찾는다.
   그런데 정확한 온도 계산은 한 번에 오래 걸려서, 바꿀 때마다 온도를 계산할 수 없다.
2. **그래서 생기는 한계**
   - 배치 중에는 "전력이 몰렸나" 정도로 대충 보고, 정확한 온도는 거의 끝난 뒤에 확인한다 → 핫스팟이 나오면 다시 배치
   - 칩은 하는 일(게임, AI 연산, 대기)마다 뜨거운 곳이 달라서, 상황이 늘수록 계산도 늘어난다
   - 온도 센서는 몇 군데만 두기 때문에, 센서가 없는 곳의 핫스팟은 놓칠 수 있다
3. **AI가 이기면**
   - 배치 그림만 보고 온도를 순식간에 예측 → 블록을 옮길 때마다 온도 확인
   - 여러 상황을 한꺼번에 확인 → 어떤 상황에서도 덜 뜨거운 배치
   - 센서 몇 개 값으로 칩 전체 온도 지도 복원 → 핫스팟을 덜 놓침
   - 프린스턴 논문의 논리와 같음: 학습 데이터 생성 약 13일 → 이후 설계 1건 약 6분
4. **이미 어디까지 와 있나** (data_check.md)
   - AI 빠른 열 예측은 연구(ThermEDGe, DeepOHeat 등)와 상용(Cadence Celsius Studio, 2024)에 이미 있음
   - 그래서 이 프로젝트는 **업계가 가는 방향을 작게 직접 만들어 확인해 보는 것**

**"AI가 이긴다"를 미리 정하지 않고, 이기는지 지는지 확인하는 것이 목적이다.**

## 3. 문제 정의
칩 위에 블록을 정해진 면적 안에 놓을 때,
**(1) 블록 사이 배선 길이(성능)와 (2) 칩 최고 온도(열)를 함께 줄이는 배치**를 찾는다.
그리고 **온도 센서 몇 개로 칩 전체 온도를 얼마나 잘 알 수 있는지** 확인한다.

- 두 목표는 부딪힌다: 뜨거운 블록끼리 붙이면 배선은 짧지만 온도가 오른다
- 회로는 몰라도 되는 수준: 블록의 크기·전력·연결 관계만 다룬다

## 4. 단계와 목표 (앞 단계만 끝나도 결과물이 남게)

### 1단계 — 칩 배치 (핵심)
- 블록 배치 → 열 시뮬레이션 → 최고 온도 + 배선 길이
- 비교: 배선만 고려한 배치 vs 열까지 고려한 배치
- 기준 방법: 기존 탐색(예: 시뮬레이티드 어닐링)

### 1.5단계 — 온도 센서 배치 (캡스톤 연결)
- 센서를 어디에 몇 개 두면 핫스팟을 놓치지 않나
- 센서 값 몇 개로 전체 온도 지도 복원
- 센서 오차가 있으면 복원이 얼마나 흔들리나

### 2단계 — AI
- 방식은 2단계 시작 때 결정 `[대기]`: 대리모델 + 탐색 / 강화학습
- AI 명분은 두 가지로만 주장
  1. 동작 상황마다 발열이 달라져도 학습한 모델을 재사용
  2. 블록을 옮길 때마다 온도를 볼 수 있을 만큼 빠름

### 3단계 — 패키지로 확장 (칩-패키지 공동설계, 순서 안 정함)
- 온도(B): 칩 위 구리 패턴으로 핫스팟 완화
- 휨(A): 리플로 온도 변화(실온 → 약 260°C)에서 판 굽힘 이론으로 휨 계산
- 선택: 레이저 어시스트 본딩 열 해석 (캡스톤 레이저 가열 계산과 연결)

## 5. 캡스톤 연결
- 연결 방식: **데이터가 아니라 개념과 본인 역할로**
  - 캡스톤 = 레이저 공정 영역 실시간 온도 측정 (이중파장 비율 방식)
  - 본인 역할: 실시간 계측 환경 구축, 오실로스코프·DAQ 연동, 전압비 보정 곡선 참여
  - 시뮬레이션 오차 분석: 비율 1% 오차 → 온도 약 54~152K 오차 (시뮬레이션) → 1.5단계 센서 오차 질문으로 연결
  - 보고서의 레이저 가열 계산(1550nm, 5W, 빔 반경 약 13μm, 흡수율 높은 SiC가 열전도율 때문에 가장 낮은 온도) → 3단계 레이저 본딩 연결
- 지킬 것
  - 캡스톤에는 검증된 실측 데이터가 없음 → 이 프로젝트의 정답 데이터로 쓰지 않음
  - 시뮬레이션 숫자에는 반드시 "시뮬레이션"을 붙임
